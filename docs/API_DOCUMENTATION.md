# FAQ Sports — API Documentation

**Last updated:** 2026-11-19 — client code at commit `1f86ac9`, checked against the real Supabase schema ([`supabase-schema.sql`](supabase-schema.sql)), its enums, delete rules, RLS policies and triggers ([DATABASE_SCHEMA.md §7](DATABASE_SCHEMA.md#7-database-rules-verified-2026-11-19)).

Related: [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) · [AUTHENTICATION.md](AUTHENTICATION.md) · [ARCHITECTURE.md](ARCHITECTURE.md#5-data-flows)

The app has no backend of its own. "The API" is the set of client functions in `api/` and `sports/*/api.ts` that call Supabase through `@supabase/supabase-js`. Each function maps to one Supabase Auth call or one PostgREST request. Mismatches with the database are labelled **D1–D18** and RLS findings **R1–R6**; details are in [DATABASE_SCHEMA.md §6](DATABASE_SCHEMA.md#6-code-vs-database-mismatches).

## 1. Conventions

- **Client:** one shared instance, `supabase`, exported from `api/supabaseClient.ts`.
- **Errors:** on error, functions `console.error` and `throw` the Supabase error (a `PostgrestError` or `AuthError`). Exceptions: `getCurrentUser` and `getUserRole` return `null` instead of throwing.
- **Callers:** screens wrap calls in `runWithGlobalLoading` and `try/catch`, and show `Alert.alert` on failure.
- **Naming:** database columns are snake_case; app types are camelCase. Mapping happens in `getTeams` and `mapPlayerRecord`.
- **IDs:** every table uses `uuid` primary keys generated by the database. Don't generate IDs in the app.
- **Permissions:** RLS policies decide what each request may do ([DATABASE_SCHEMA.md §7.3](DATABASE_SCHEMA.md#73-row-level-security-policies)). A denied insert fails with `42501`; a denied update or delete **succeeds with 0 rows changed**, so check the affected rows (`.select()` after the write) before reporting success.
- **Signed out = `anon`:** on iOS/Android the session probably isn't persisted ([AUTHENTICATION.md §4.2](AUTHENTICATION.md#42-session-persistence)), so after a restart writes go out as `anon` and fail even for admins.
- **`updated_at`** is set by triggers; never send it.
- **No pagination, no column selection** (except grounds), **no update functions**, **no realtime**.

## 2. Configuration

`api/supabaseClient.ts`:

```ts
const SUPABASE_URL = process.env.EXPO_PUBLIC_SUPABASE_URL || 'https://gflkukmbxjiggvobvitb.supabase.co';
const SUPABASE_KEY =
  process.env.EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY || process.env.EXPO_PUBLIC_SUPABASE_ANON_KEY;
if (!SUPABASE_KEY) throw new Error('Missing EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY ...');
export const supabase = createClient(SUPABASE_URL, SUPABASE_KEY);
```

| Variable | Required | Purpose |
|----------|----------|---------|
| `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | yes (or the legacy one) | Publishable client key (`sb_publishable_...`). |
| `EXPO_PUBLIC_SUPABASE_ANON_KEY` | fallback | Legacy anon JWT. |
| `EXPO_PUBLIC_SUPABASE_URL` | no | Overrides the project URL. |

The client is created with default options: no `auth.storage`, so see [AUTHENTICATION.md §4](AUTHENTICATION.md#4-session-handling).

## 4. Request examples

Each example shows the app call, then the HTTP request supabase-js sends. `$KEY` is the publishable key and `$JWT` the signed-in user's access token (without a session, supabase-js sends the publishable key as the bearer). Every REST request carries:

```http
apikey: $KEY
Authorization: Bearer $JWT
```

Never paste a real key into docs, tickets or logs. Examples marked **not in code** show the correct request for the real schema; they are not implemented.

### 4.1 Sign up

```ts
await signUp('jane.doe@example.com', 'secret123', 'Jane Doe');
```

```http
POST https://gflkukmbxjiggvobvitb.supabase.co/auth/v1/signup
Content-Type: application/json

{ "email": "jane.doe@example.com", "password": "secret123", "data": { "full_name": "Jane Doe" } }
```

Creates a row in `auth.users`. The `on_auth_user_created` trigger then runs `handle_new_user()`, which presumably creates the `profiles` row; the role it assigns is **Unknown** ([DATABASE_SCHEMA.md §7.4](DATABASE_SCHEMA.md#74-triggers), [§8](DATABASE_SCHEMA.md#8-still-unknown--queries-to-run)).

### 4.2 Sign in and load role

```ts
await signIn('jane.doe@example.com', 'secret123');
const role = await getUserRole('jane.doe@example.com'); // 'admin' | 'player' | null
```

```http
POST /auth/v1/token?grant_type=password
{ "email": "jane.doe@example.com", "password": "secret123" }
```

```http
GET /rest/v1/profiles?select=role&email=eq.jane.doe%40example.com
Accept: application/vnd.pgrst.object+json
```

RLS ("Users read own profile") only returns the caller's own row, so this works only for the signed-in user's own email. `.single()` returns error `PGRST116` if that row is missing. `profiles.role` accepts any text, so anything other than `'admin'`/`'player'` is treated as no role.

**Security:** the same user can change their own role, because "Users update own profile" has no column restriction (R1):

```http
PATCH /rest/v1/profiles?id=eq.<own id>
{ "role": "admin" }      → succeeds today
```

**Not in code** — lookup by the auth user's ID, which is the primary key:

```ts
const { data: { user } } = await supabase.auth.getUser();
const { data } = await supabase.from('profiles').select('role, full_name').eq('id', user!.id).single();
```

### 4.3 List teams

```ts
const teams = await getTeams();
```

```http
GET /rest/v1/teams?select=*&order=name.asc
```

Response row → app `Team`:

```json
{ "id": "6f1c…", "name": "Falcons", "short_name": "FAL", "color": "#2ECC71", "logo_url": null,
  "captain_player_id": null, "created_at": "…", "updated_at": "…" }
```

```ts
{ id: '6f1c…', name: 'Falcons', shortName: 'FAL', color: '#2ECC71', logo: null, players: [], captain: null }
```

`players` is always `[]`; use `useData().getTeamPlayers(team.id)`.

### 4.4 Add a team

```ts
await uploadTeamInfo({ name: 'Falcons', short_name: 'FAL', color: '#2ECC71' });
```

```http
POST /rest/v1/teams
Content-Type: application/json

{ "name": "Falcons", "short_name": "FAL", "color": "#2ECC71" }
```

| Failure | Postgres code | Cause |
|---------|---------------|-------|
| Name already used | `23505` | `teams.name` is unique |
| Bad colour | `23514` | `color` must be `#RGB` or `#RRGGBB` |
| Not signed in | `42501` | Insert policy is for `authenticated` only |

Any signed-in user can add a team, including players (R2).

### 4.5 Add a player (two requests)

```ts
const playerId = await uploadPlayerInfo({
  name: 'Jane Doe',
  team_id: teamId,           // uuid or null
  position: 'All-rounder',   // 'Batsman' | 'Bowler' | 'All-rounder' | 'Wicketkeeper' | null
  batting_style: 'right',    // 'right' | 'left' | null
  bowling_style: 'Off spin'  // free text or null
});
await uploadPlayerStats({ player_id: playerId, matches: 0, runs: 0, /* …all zero… */ best_bowling_runs: 0 });
```

```http
POST /rest/v1/players?select=id
Prefer: return=representation
Accept: application/vnd.pgrst.object+json

{ "name": "Jane Doe", "team_id": "6f1c…", "position": "All-rounder", "batting_style": "right", "bowling_style": "Off spin" }
```

```http
POST /rest/v1/player_stats

{ "player_id": "9a2e…", "matches": 0, "runs": 0, "balls": 0, "wickets": 0, "catches": 0, "run_outs": 0,
  "stumpings": 0, "highest_score": 0, "best_bowling_wickets": 0, "fifties": 0, "centuries": 0,
  "batting_average": 0, "strike_rate": 0, "economy_rate": 0, "goals": 0, "assists": 0, "wins": 0,
  "best_bowling_runs": 0 }
```

- `position` is enum `player_position`: `Batsman`, `Bowler`, `All-rounder`, `Wicketkeeper` (case-sensitive). The form accepts free text, so anything else fails with `22P02` (D3).
- `players` and `player_stats` have **no insert policy** (R5). If RLS is on for them, both inserts fail with `42501` for everyone; if it's off, anyone with the key can write them. Which applies is **Unknown**.
- `best_bowling_wickets` / `best_bowling_runs` are text columns; `0` is stored as `"0"` (D6).
- All `player_stats` columns default to 0, so `{ "player_id": "…" }` alone would be enough.
- No `player_ratings` row is created (D10).
- Not atomic: if the second request fails, the player exists with no stats row.

### 4.5a Change a player's team

```ts
await updatePlayerTeam(playerId, teamId); // teamId = null for "No Team"
```

```http
PATCH /rest/v1/players?id=eq.<playerId>&select=id
Prefer: return=representation

{ "team_id": "6f1c…" }
```

An empty response means RLS blocked the update (there is no UPDATE policy on `players`); the function throws so the screen shows an error instead of a false success.

### 4.6 List players

```ts
const players = await getPlayers();
```

```http
GET /rest/v1/players?select=*&order=name.asc
```

`players` has no stat columns, so `mapPlayerRecord` sees `undefined` for every stat and shows 0 (D1). Ratings are hard-coded to 50 and `lastFivePerformances` to `[]`.

**Not in code** — embed the one-to-one tables:

```ts
supabase
  .from('players')
  .select('*, player_stats(*), player_ratings(batting, bowling, fielding, overall)')
  .order('name');
```

```http
GET /rest/v1/players?select=*,player_stats(*),player_ratings(batting,bowling,fielding,overall)&order=name.asc
```

Because `player_id` is unique in both tables, PostgREST returns each as a single object (or `null`), not an array.

### 4.7 Archive a team (teams are never deleted)

```ts
await archiveTeam(teamId);   // restoreTeam(teamId) undoes it
```

```http
POST /rest/v1/rpc/archive_team   { "p_team_id": "<teamId>" }
```

- Admins only; the function raises `42501` otherwise. Players are kept and unassigned; the team row, its match history (`player_match_stats`) and awards stay. The notes below describe the old DELETE, kept for reference.

- **Permission:** the only delete policy allows one hard-coded user ID. For every other user, including other admins, the request returns success and **deletes nothing** (R3).
- **Effects when allowed:** players are kept with `team_id` set to null; captain, favourite-team and toss/winner references are cleared; `tournament_teams` rows are deleted.
- **Blocked** with `23503` if the team appears as `team_a_id`/`team_b_id` of a saved match or as an innings' batting/bowling team (`ON DELETE RESTRICT`).
- The Teams screen calls this twice without `await`, so errors become unhandled rejections and the "deleted successfully" alert always shows.

### 4.8 Delete a player (current, buggy)

```ts
await deletePlayerInfo(playerId);
```

```http
DELETE /rest/v1/teams?id=eq.<playerId>
```

This targets `teams`, so it deletes nothing (and only the one user allowed to delete teams could delete anything here).

A corrected `DELETE /rest/v1/players?id=eq.<playerId>`:

- has **no delete policy** on `players`, so it deletes nothing if RLS is on (D18);
- when allowed, cascades to `player_stats`, `player_ratings`, `player_performances`, `match_squads` **and the player's rows in past batting and bowling scorecards and fall of wickets**, and clears the player from ball events and captaincy ([DATABASE_SCHEMA.md §7.2](DATABASE_SCHEMA.md#72-delete-rules)).

### 4.9 Grounds

```ts
const names = await getGrounds();             // ['Car Park', 'Main Oval']
await addGround('Main Oval', 'Level 2 roof'); // location optional
```

```http
GET  /rest/v1/grounds?select=name&order=name.asc
POST /rest/v1/grounds   { "name": "Main Oval", "location": "Level 2 roof" }
```

`name` is unique (`23505` on duplicates). Any signed-in user can add a ground (R2). There's no delete policy, so a server-side delete isn't possible yet. Matches reference grounds by `ground_id`, so `getGrounds` will need to return `id` once matches are saved (D5).

## 5. Postgres errors to handle

| Code | Meaning | Where it happens today |
|------|---------|------------------------|
| `23505` | Unique violation | Duplicate team or ground name; second `player_stats` row for a player |
| `23503` | Foreign key violation | Deleting a team that has played a saved match (`RESTRICT`); inserting with an unknown team or player ID |
| `23514` | Check violation | Team colour not `#RGB`/`#RRGGBB`; `total_overs` ≤ 0 |
| `22P02` | Invalid input syntax | Text not in an enum (`position`, `status: 'cancelled'`); a non-uuid ID such as `match_123` or a mock ID like `t1` |
| `42501` | Insufficient privilege (RLS) | Insert with no matching policy: signed out, or a table with no insert policy |
| *(none)* | Update/delete matched 0 rows | RLS denied it (e.g. team delete by anyone but the one allowed user). Check affected rows |
| `23502` | Not-null violation | Missing `name`, `team_a_id`, etc. |
| `PGRST116` | `.single()` got 0 or many rows | Role lookup with no or duplicate `profiles` rows |
| `42P01` / `PGRST205` | Table not found | `ball_info` |

Show a specific message for at least `23505`, `23503` and `42501`, and treat a 0-row update or delete as a failure; today every failure shows a generic "Failed to …" and 0-row deletes show "deleted successfully".

## 7. Adding a new API function

Follow the existing pattern:

```ts
// api/groundApi.ts
export const deleteGround = async (id: string): Promise<void> => {
  const { error } = await supabase.from('grounds').delete().eq('id', id);
  if (error) {
    console.error('Error deleting ground:', error);
    throw error;
  }
};
```

(An example of the pattern, not existing code.)

- Shared data → `api/<entity>Api.ts`; sport-specific → `sports/<sport>/api.ts`.
- Check table and column names against [`supabase-schema.sql`](supabase-schema.sql).
- Map snake_case rows to app types inside the function.
- Throw on error; let the caller show the message.
- Don't log row data ([AUTHENTICATION.md §7](AUTHENTICATION.md#7-security-findings)).
- Update this page and [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) in the same change.
